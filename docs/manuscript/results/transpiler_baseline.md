# Transpiler baseline: a rule-based C->Go transpiler does not clear the bar

Manuscript claim **C5** (primary counterfactual / desk-reject control).

## 1. Why this control exists

The central claim of the project is that LLM agents produced **53 byte-exact,
idiomatic, memory-safe, cgo-free Go CLIs** from C, C++, and Perl originals. The
obvious reviewer challenge is: *"a mechanical, non-LLM transpiler could have done
this; the LLM is doing nothing special."* This document isolates the LLM
contribution by showing that a representative **non-LLM, rule-based automated
C->Go transpiler does not reach the bar the LLM agents reached.**

The transpiler under test is **c2go** (`github.com/elliotchance/c2go`,
v0.26.11) — the most mature open-source rule-based C->Go source-to-source
translator. It is the strongest available stand-in for the "just transpile it"
hypothesis. C2Rust is the analogous tool in the Rust ecosystem and shares the
same architecture (clang AST -> mechanical lowering to `unsafe` code), so the
conclusions transfer.

### The bar (four criteria the LLM-produced CLIs met)

A port "clears the bar" only if it meets **all four**:

1. **Compiles** — the generated Go builds (`go build` / `go vet`).
2. **Runs** — the built program executes on a real input.
3. **Byte-parity** — its output is byte-for-byte identical to the original
   tool on the same input (the project's parity gate).
4. **Idiomatic + memory-safe** — idiomatic Go that does **not** use `unsafe`,
   does **not** use cgo, and is built on the standard library plus the
   in-tree `pkg/htsgo` libraries (the project's stated quality bar).

## 2. Experimental design

| Element | Value |
| --- | --- |
| Transpiler | c2go v0.26.11 (`go install github.com/elliotchance/c2go@latest`) |
| Frontend | clang (c2go shells out to `clang` to dump the C AST) |
| Input A (best case) | a trivial `hello.c` (`printf` + `return 0`) |
| Input B (real) | `reference_code/sickle/src/sickle.c` (pure-C, vendored upstream) |
| Input C (real, build-coupled) | `reference_code/htslib/bgzip.c` |
| Evaluation | the four bar criteria above |
| Harness | `scripts/transpiler/run_c2go_baseline.sh` (reproducible, no LLM) |

`sickle` is chosen as the *real* input because it is genuine, vendored,
pure-C upstream bioinformatics code — and pure C is the **only** language c2go
even claims to support, so it is the transpiler's best realistic case. `bgzip.c`
is included to show a second, orthogonal failure mode (build-system coupling).

## 3. Actual findings (this environment)

c2go **installed successfully** (`go install ...@latest` succeeded; the binary
landed at `$(go env GOPATH)/bin/c2go`). clang 18.1.3 and gcc 13.3 are present.
So the install step is **not** the blocker — the transpiler itself is.

Running the harness (`scripts/transpiler/run_c2go_baseline.sh`):

### 3.1 Trivial `hello.c` -> c2go panics

```text
$ c2go transpile -o hello.go hello.c
panic: unknown node type: 'BuiltinAttr 0x... <<invalid sloc>> Implicit 916'
    github.com/elliotchance/c2go/ast.Parse(...)
        .../c2go@v0.26.11/ast/ast.go:294
```

No `hello.go` is produced. c2go cannot transpile *even a hello-world*. The
cause is concrete and verifiable: modern clang (>= 10) emits `BuiltinAttr`
nodes in its AST dump (clang 18 emits 40 of them for `hello.c` alone), and
c2go — last released in 2021 and pinned to a 2018 `golang.org/x/tools` — has
no handler for that node type (`ls .../c2go/ast/ | grep -i builtin` shows only
`builtin_type.go`; there is no `builtin_attr.go`). It therefore panics. This
reproduces on clang 14 as well (the oldest clang in this distro's repos);
clang 9, the last version c2go officially targeted, is not available here.

### 3.2 Real `sickle.c` -> c2go panics

```text
$ c2go transpile -o sickle.go reference_code/sickle/src/sickle.c
panic: unknown node type: 'value: Int 235'   (or 'BuiltinAttr ...')
    github.com/elliotchance/c2go/ast.Parse(...)
        .../c2go@v0.26.11/ast/ast.go:294
```

Same root cause (unmodelled clang-AST node types). The specific node named in
the panic varies between runs because c2go parses AST lines across parallel
goroutines and aborts on whichever unknown node it reaches first; the
underlying failure is identical. **No Go is produced.**

### 3.3 Real `bgzip.c` -> fails before c2go even sees it

```text
$ c2go transpile -o bgzip.go reference_code/htslib/bgzip.c
Error: issue running preprocessor: ...
  reference_code/htslib/bgzip.c:25:10: error: 'config.h' file not found
```

htslib's `bgzip.c` `#include <config.h>`, a header **generated by htslib's
`./configure`**. The transpiler has no concept of a build system, so it cannot
even preprocess the translation unit. This is an orthogonal, structural reason
real-world C does not feed cleanly into a source-to-source transpiler.

### 3.4 Result table

| Input | Transpiles? | Compiles | Runs | Byte-parity | Idiomatic + memory-safe |
| --- | --- | --- | --- | --- | --- |
| `hello.c` (trivial) | No (AST panic) | n/a | n/a | n/a | n/a |
| `sickle.c` (real C) | No (AST panic) | n/a | n/a | n/a | n/a |
| `bgzip.c` (real C) | No (preprocess) | n/a | n/a | n/a | n/a |

On this environment, c2go fails the bar at the **very first** criterion: it does
not even emit Go. That is an honest, reproducible result — captured by the
committed harness — not a contrived one.

## 4. The output quality, on its own terms (evidence the bar is unreachable in principle)

The environment-specific clang-version panic could be read as a mere packaging
problem, so it is important to evaluate c2go on the output it produces **when it
does work**. c2go's own README publishes the canonical translation of a prime-
number C program. That published output is the tool functioning as designed:

```go
package main

import "unsafe"
import "github.com/elliotchance/c2go/noarch"

var stdin *noarch.File
var stdout *noarch.File
var stderr *noarch.File

func main() {
    __init()
    var n int
    var c int
    noarch.Printf([]byte("Enter a number\n\x00"))
    noarch.Scanf([]byte("%d\x00"), (*[1]int)(unsafe.Pointer(&n))[:])
    // ...
}
```

This is c2go at its **best**, and it still fails criterion (4) categorically:

- It `import "unsafe"` and performs manual pointer casts
  (`(*[1]int)(unsafe.Pointer(&n))[:]`) for ordinary `scanf`. The project's bar
  is **no `unsafe`**.
- Every libc call is routed through a bundled **`noarch`** shim package (a
  13-file Go re-implementation of a libc subset: `noarch.Printf`,
  `noarch.Scanf`, `noarch.File`, `noarch.Stdin`...). The output is therefore
  **not built on the standard library / `pkg/htsgo`**; it carries its own
  runtime. The project's bar is stdlib + in-tree libraries.
- The structure is transliterated C, not idiomatic Go: C-style `for c = 2; ...`
  loops with the increment hoisted into an inline `func() int { c += 1; return
  c }()` closure, null-terminated `[]byte("...\x00")` string literals, a
  hand-rolled `__init()`. No `error` returns, no slices/maps idiom, no Go
  package structure.

So even granting c2go a working frontend, its **design** produces
unsafe-using, libc-shim-dependent, non-idiomatic Go. It cannot meet criterion
(4) by construction, and the project never observed it producing a parity-tested,
runnable port (criteria 2–3) for any real input.

## 5. Scope: the C++ and Perl originals cannot be transpiled at all

c2go and C2Rust-class tools support **C only — no C++**. This is decisive for
this codebase, because a large fraction of the upstream originals are **not C**:

- **bedtools** is C++ (`reference_code/bedtools/src` contains 162 `.cpp`
  files). samtools and bcftools also carry C++.
- **prinseq** is Perl (`reference_code/prinseq/prinseq-lite.pl`).

No rule-based C->Go transpiler can even ingest these sources. The ~24 samtools
subcommands, ~24 bcftools subcommands, ~37 bed* tools, and the Perl-derived
prinseq port are **outside the reach of any such transpiler by construction** —
they could never appear in a transpiler-built corpus at all.

## 6. Connecting back to the LLM-contribution claim

Even in the **best case** — a small, pure-C translation unit, the only thing a
rule-based transpiler claims to handle — c2go on this environment produces no
Go at all, and where it does work (its own published example) the output uses
`unsafe`, depends on a bundled libc shim, and is transliterated rather than
idiomatic. It therefore fails the "idiomatic + memory-safe + stdlib-based"
criterion in principle and the byte-parity / runnable criteria in practice.
For the C++ originals (bedtools, much of samtools/bcftools) and the Perl
original (prinseq), no rule-based C->Go transpiler exists at all, so the
transpiler corpus would be empty for those tools.

The LLM agents, by contrast, produced idiomatic, cgo-free, `unsafe`-free Go
across **C, C++, and Perl** originals and passed a byte-exact upstream-parity
gate (re-executed independently in CI). The gap between "the mechanical tool
emits nothing, or unsafe libc-shim transliteration for trivial C only" and
"the agents cleared all four criteria across three source languages" is the
isolated LLM contribution this control was designed to measure.

### Calibration / threats to validity

- The c2go *panic* observed here is partly an environment artifact (modern
  clang). We do not claim c2go can **never** emit Go — only that (a) it could
  not on the available toolchain, and (b) its documented best-case output still
  fails criterion (4). The argument rests on the **design** limitations (unsafe,
  noarch libc shim, non-idiomatic transliteration, C-only), which the README
  evidence establishes independently of the panic.
- We tested one representative transpiler. The claim generalizes only insofar
  as C2Rust-class tools share the same clang-AST-to-`unsafe` architecture; a
  reviewer with a different transpiler can rerun the committed harness.
- Criteria (2) runs and (3) byte-parity were not reachable here because no Go
  was produced; the harness marks them as manual steps to be completed if a
  future toolchain gets c2go past the AST stage.

## 7. Reproducing

```bash
scripts/transpiler/run_c2go_baseline.sh
```

The script installs c2go, runs it on `hello.c` and the vendored `sickle.c`,
and prints the four-criteria evaluation. It requires only Go and clang; it
uses **no LLM**. See its header for environment overrides (`C2GO_BIN`,
`CLANG_BIN`) and the note on clang-version compatibility.
